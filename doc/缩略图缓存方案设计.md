# 缩略图缓存方案设计

## 1. 现状梳理

### 1.1 系统照片源（`PhotoThumbnailProvider` → `PHCachingImageManager`）

- 资产查找结果有 `assetCache: NSCache<NSString, PHAsset>`（内存，本次启动有效）。
- 缩略图本身**不经过我们自己的缓存**，直接交给 `PHCachingImageManager.requestImage` /
  `startCachingImages`。PhotoKit 在
  `~/Pictures/Photos Library.photoslibrary/resources/derivatives/` 维护一份
  **持久化、多档位的 JPEG 缩略图缓存**（系统级，重启 App、重启电脑都还在），
  我们的 `startCaching`/`stopCaching` 只是给 PhotoKit「预热提示」。
- 结论：**系统源的缩略图持久化缓存已经由 PhotoKit 解决了**，我们不需要、
  也不应该重复实现——重复缓存只会占用双份磁盘空间。

### 1.2 本地 / 外部目录源（`LocalThumbnailProvider`）

```swift
private let cache = NSCache<NSString, NSImage>()   // countLimit = 1000
let keyString = "\(cacheKey)@\(Int(maxPixel))"
```

问题：

1. **纯内存、随进程退出清空**——每次启动 App，本地照片墙的缩略图都要重新
   `ImageIO` 解码一遍。
2. **Key 里带精确 `maxPixel`**——`maxPixel` 由网格列数 × 屏幕 `backingScaleFactor`
   算出（见 `PhotoGridViewController.thumbnailTargetSize()`），**只要切换网格密度，
   `maxPixel` 几乎必然变化**，命中率归零，等于重新生成全部缩略图。
3. **只有数量上限（1000 条），没有字节上限**——大图（4K 截图、RAW 预览）撑爆
   内存时无法预期。
4. **没有清理机制、没有可配置项**。

这正是用户报告的「切换网格列数 / 重新打开 App / 切换搜索条件都要重新生成缩略图」
的根因。

## 2. 参考：macOS 系统照片的做法

- 系统照片库通过 `resources/derivatives/` 持久化保存**多档位**（缩略图、预览图、
  各类编辑派生图）的 JPEG，按资产 UUID 组织，配合数据库记录每个派生图的尺寸/版本——
  **档位是有限的几档，不是任意尺寸**，这样不同浏览场景（缩略图墙、详情大图）
  都能复用同一份磁盘缓存。
- macOS 另有独立的 QuickLook 缩略图缓存（`com.apple.QuickLook.thumbnailcache`），
  同样是「磁盘持久化 + 数据库索引 + 后台清理」的结构。

可借鉴的三点：**(a) 落盘持久化**，**(b) 尺寸分「档位」而非任意精确像素**，
**(c) 用轻量索引记录元数据以支持 LRU 清理**。

Sources:
- [What is the "derivatives" folder in the Photos Library](https://discussions.apple.com/thread/8577003)
- [Your encrypted photos revealed in macOS cache](https://wojciechregula.blog/post/your-encrypted-photos-in-macos-cache/)

## 3. 方案设计

只针对 **本地 / 外部目录源**（系统源继续交给 PhotoKit）。

### 3.1 两级缓存

- **L1：内存** —— 现有 `NSCache<NSString, NSImage>`（解码后的 `NSImage`），
  保持不变，命中最快。
- **L2：磁盘** —— 新增 `DiskThumbnailCache`，存储**已解码降采样后的 JPEG**
  （质量 0.85，比原图小得多，解码比重新跑一遍 `ImageIO` 全套降采样快很多）。

读取顺序：L1 命中 → 直接用；L1 未命中、L2 命中 → 解码 JPEG 写回 L1；
都未命中 → 走现有 `ImageIO` / 视频抽帧逻辑，结果同时写 L1 + L2。

### 3.2 尺寸分档（解决「切换网格列数就失效」）

不再用精确 `maxPixel` 做 key，而是向上取整到固定档位：

```swift
enum ThumbnailBucket: Int, CaseIterable {
    case xs = 160   // 最密网格
    case sm = 320
    case md = 640
    case lg = 1024
    case xl = 2048  // 查看器静态预览

    static func bucket(for maxPixel: CGFloat) -> ThumbnailBucket {
        allCases.first { CGFloat($0.rawValue) >= maxPixel } ?? .xl
    }
}
```

切换网格列数时，`maxPixel` 多数情况落在同一档位内，直接命中 L1/L2，
**不会重新生成**；只有跨档位（比如从「极密网格」一口气拉到「极疏网格」）
才会触发一次新档位的解码——而且该档位一旦生成，以后同密度即可复用。

### 3.3 Key 与磁盘布局

```
~/Library/Application Support/MantaPhotos/ThumbnailCache/
  <bucket>/<sha256(cacheKey)>.jpg
```

- `cacheKey` 沿用现有 `asset.id`（已能唯一标识一个本地资产）。
- 文件修改时间变化（用户在 Finder 里替换了同名文件）则视为新版本——
  `cacheKey` 里追加文件 `mtime`，自然失效旧条目，无需显式失效逻辑。

### 3.4 索引与 LRU 清理

新增数据库表 `thumbnail_cache_index`（沿用现有 GRDB/`AppSettingsRepository`
所在数据库，做一次轻量迁移）：

| 列 | 说明 |
|---|---|
| `key` (PK) | `sha256(cacheKey)_bucket` |
| `bucket` | 档位 |
| `size_bytes` | 文件大小 |
| `last_access_at` | 最近一次读取时间 |

- 每次 L2 命中 / 写入时更新 `last_access_at`（异步、不阻塞主流程）。
- App 启动时 + 每次写入后台异步检查：`sum(size_bytes)` 是否超过用户设置的
  上限；超过则按 `last_access_at` 升序删除，直到回落到上限的 90%
  （留一点缓冲，避免每次都触发清理）。
- 「立即清理」：直接删除整个 `ThumbnailCache` 目录 + 清空索引表 + 清空 L1
  `NSCache`。

### 3.5 设置项（`SettingsPageView` 新增「缓存」分区）

```
┌ 缓存 ──────────────────────────────────┐
│ 缩略图缓存占用：1.2 GB                    │
│ 缓存上限：[ 2 GB ▾]  (500MB/1/2/5GB/不限)│
│ ☑ 超出上限时自动清理最久未访问的�caches    │
│ [立即清理缩略图缓存]                      │
│ 提示：系统照片库的缩略图由 Photos 管理，    │
│ 不计入此处统计。                          │
└────────────────────────────────────────┘
```

`AppSettingsSnapshot` 新增：

```swift
var thumbnailCacheLimitBytes: Int64 = 2 * 1_024 * 1_024 * 1_024 // 默认 2GB
var thumbnailCacheAutoCleanEnabled: Bool = true
```

按现有 `app_settings` key/value 表模式持久化（`cache.thumbnailLimitBytes`、
`cache.thumbnailAutoClean`），与主题/语言等设置走同一条路径，无需新表。

### 3.6 与现有「优先级反转」修复的关系

L2 的 JPEG 编解码同样应经由 `ThumbnailLoadingQueue.run`（已调整为 `.utility`，
见本次同批修复），避免引入新的 QoS 反转。

## 4. 实施清单（后续编码任务）

1. 新增 `Infrastructure/Photos/DiskThumbnailCache.swift`：
   - `actor` 或 `final class ... : @unchecked Sendable`，封装读/写/统计大小/清理。
   - `ThumbnailBucket` 枚举。
2. 改造 `LocalThumbnailProvider.requestThumbnail`：先查 L1，再查 L2，
   都未命中再走现有解码逻辑；解码结果回填 L1 + L2。
3. `Infrastructure/Database`：新增 `thumbnail_cache_index` 表迁移；
   `AppSettingsSnapshot` / `AppSettingsRepository` 增加两个新字段。
4. `SettingsPageView`：新增「缓存」Section（占用大小展示、上限 Picker、
   自动清理开关、立即清理按钮）。
5. App 启动流程（`AppBootstrapper` 或 `AppState` 初始化处）：异步触发一次
   LRU 检查（不阻塞首屏）。

## 5. 验证清单

- 切换网格密度（极密 ↔ 极疏）：仅跨档位时短暂重新生成，同档位内零等待。
- 重新打开 App：本地照片墙缩略图直接命中磁盘缓存，明显快于首次导入。
- 切换搜索条件（筛选结果集变化）：不影响缓存——key 与筛选条件无关。
- 设置里调小缓存上限并点击「立即清理」：磁盘占用应降到新上限以内。
- 长时间使用后磁盘占用不超过设置的上限。
