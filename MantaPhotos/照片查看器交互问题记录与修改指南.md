# 照片查看器：手势 / 快捷键反复失效问题记录与修改指南

> 对应代码：
> - `MantaPhotos/Sources/MantaPhotosMac/Presentation/Photos/PhotoViewerView.swift`
>   （SwiftUI 布局、状态、业务逻辑）
> - `MantaPhotos/Sources/MantaPhotosMac/Presentation/Photos/PhotoViewerInteropViews.swift`
>   （AppKit interop：`HostedOverlay`/`ZoomableImageView`/`SwipeAwareScrollView`/
>   `LivePhotoPlayerView`/`ViewerKeyCommandsView`，2026-06-13 起单独拆出）
>
> 本问题已连续出现 **4 次**（任务 #26 重构查看器时引入、任务 #30“修复一次”、
> 第 3 次报告手势+快捷键全部失效、第 4 次报告“首次打开延迟生效”+“按钮位置
> 错乱”）。本文档的目的是让以后任何人改这两个文件前，先看一眼这里，避免
> 第 5 次重复同一类坑。

## 一句话总结

**查看器是 SwiftUI 纯视图 + `NSViewRepresentable`（NSScrollView/NSImageView）混合的视图树。
AppKit 的事件分发（鼠标 hitTest、键盘第一响应者）和 SwiftUI 的 ZStack 视觉层级是两套独立的规则，
只要在这个文件里调整覆盖层结构，就有很大概率在不经意间打破其中一套规则。**

## 问题史

### 第 1 次（任务 #26 重构时引入）

`viewerChrome`（包含返回/上下张/播放/收藏/删除/信息等按钮的纯 SwiftUI 视图）
直接作为 `ZStack { mediaContent; viewerChrome }` 的子视图。

- `mediaContent` 是 `ZoomableImageView`（`NSViewRepresentable` 包装的真实
  `NSScrollView` + `NSImageView`）。
- `viewerChrome` 是纯 SwiftUI，渲染为父 `NSHostingView` **自身**的图层内容，
  不是独立 NSView。

AppKit 的 `NSView.hitTest(_:)` 默认实现：**先测试真实子视图，所有子视图都返回
`nil` 才轮到自身内容**。因此与 `NSScrollView` 重叠区域内的按钮点击和依赖
`performKeyEquivalent` 的快捷键，全部被 `NSScrollView` 截获——与 SwiftUI 里
`viewerChrome` "画在 ZStack 上层" 的视觉顺序无关。

**症状**：按钮点不动、快捷键不响应。

### 第 2 次（任务 #30，引入 `HostedOverlay`）

把整个 `viewerChrome`（一个内部用 `Spacer()` 撑开、上下各一条工具栏的
`VStack`）包成**一个** `HostedOverlay`（独立 `NSHostingView`），让它成为与
`NSScrollView` 同级、且排在其后（z-order 更上层）的真实子视图。

理论依据（**事后证明不完全成立**）：假设 `NSHostingView` 对自身空白区域的
`hitTest` 会返回 `nil`，点击穿透到下层 `NSScrollView`。

但 `viewerChrome` 这个 `VStack` 内部带 `Spacer()`，是 flexible 的——SwiftUI 会
把它在 ZStack 里撑满到跟 `mediaContent` 一样大。于是这个 `HostedOverlay` 的
`NSHostingView.frame` **覆盖了整个查看器区域**，而 `NSHostingView` 对自身
`bounds` 内任意一点（包括 `Spacer` 空白区）的默认 `hitTest` 实际返回的是
`self`，并不会穿透。

**症状**（本次报告）：
- 按钮本身能点（在 `HostedOverlay` 范围内，理所当然）。
- 但图片区域的捏合缩放 / 拖拽平移 / 双击缩放 / 双指滑动切图（全部由
  `SwipeAwareScrollView`/`NSScrollView` 提供）**全部失效**——因为铺满全屏的
  `HostedOverlay` 在 z-order 上盖住了 `NSScrollView`，鼠标和触控板事件全被
  `HostedOverlay` 截获。
- 无修饰键快捷键（方向键/Space/T/F/D/I）也不可靠——因为点击图片区域时，第一
  响应者落在了空的 `HostedOverlay` 的 `NSHostingView` 上，而不是
  `SwipeAwareScrollView` 或任何能处理这些快捷键的视图。

### 第 3 次（本次修复，2026-06-13）

同时修好「手势」和「快捷键」，并且让修复对未来的覆盖层调整更**鲁棒**（不再
依赖"猜测" AppKit 的 hitTest/第一响应者细节）。

#### 手势修复：拆分覆盖层为"自然高度的窄条"

不再用一个铺满全屏的 `HostedOverlay`。改成：

```swift
VStack(spacing: 0) {
    HostedOverlay { viewerTopBar }
    Spacer()
    HostedOverlay { viewerBottomBar }
}
```

`viewerTopBar` / `viewerBottomBar` 都是"自然高度"的 `HStack`（非 flexible，
不带 `Spacer()` 撑满自身），SwiftUI 只会给对应的 `HostedOverlay` 分配各自内容
的高度——因此两个 `NSHostingView` 的 `frame` 只覆盖屏幕最上/最下的一条"窄带"，
中间大片图片区域**没有任何覆盖层 NSView**，`NSScrollView` 的手势完全不受影响。

#### 快捷键修复：专用 `ViewerKeyCommandsView`，不再用 `.keyboardShortcut`

新增 `ViewerKeyCommandsView`（`NSViewRepresentable` → `KeyCommandView: NSView`）：

- `frame` 固定 0x0，`hitTest` 永远返回 `nil`——对鼠标/手势零影响。
- `viewDidMoveToWindow` 时 `window?.makeFirstResponder(self)`。
- `updateNSView` 里检测第一响应者是否被抢走，若是则异步抢回来（自愈）。
- `keyDown(with:)` 直接匹配 `keyCode`/`charactersIgnoringModifiers`，分发到
  对应的回调闭包：Esc → 返回，←/→ → 上一张/下一张，Space → 播放/暂停（即使
  当前媒体不可播放也要吞掉，避免系统提示音），T/F/D/I → 照片篓/收藏/删除/信息。
- 只处理**无修饰键**按键；带 Cmd/Option/Control/Shift 的组合键交还系统
  （`super.keyDown`），避免抢系统/菜单快捷键。

配套修改：`SwipeAwareScrollView` 显式 `override var acceptsFirstResponder: Bool { false }`，
确保点击图片时不会把第一响应者从 `ViewerKeyCommandsView` 抢走。

### 第 4 次（2026-06-13）：首次打开延迟生效 + 按钮位置错乱 + 拆文件

#### 问题 A：查看器第一次打开时，手势/快捷键要过一会才生效

**根因**：查看器刚出现的那一帧，`window` 还没有成为 key window（呈现动画/
窗口焦点切换尚未完成）。此时 `ViewerKeyCommandsView.KeyCommandView`
在 `viewDidMoveToWindow` 里调用 `window.makeFirstResponder(self)`
**调用本身会成功**（`window.firstResponder === self`），但 AppKit 在
`window.isKeyWindow == false` 期间不会把 `keyDown` 投递给它。在那之前，
`updateNSView` 里的「自愈」逻辑只有在 SwiftUI 触发新一轮 `body` 求值
（例如缩略图异步加载完成）时才会被调用一次，所以表现为"过一会才生效"。

**修复**（`PhotoViewerInteropViews.swift` → `KeyCommandView`）：
- `viewDidMoveToWindow` 里除了立即 `makeFirstResponder` 一次，额外注册
  `NSWindow.didBecomeKeyNotification` 观察者：窗口真正变成 key window 的
  那一刻，再抢一次第一响应者（`handleWindowDidBecomeKey`）。
- 再加一道 `DispatchQueue.main.async` 重试，覆盖"窗口已是 key，但 SwiftUI
  在同一帧布局里把第一响应者设置成了别的视图"这种边缘情况。
- `deinit` 里移除通知观察者，避免内存泄漏/野指针回调。

#### 问题 B：返回按钮 / 上下张按钮 / 底部信息栏挤在中间，而不是贴边角

**根因**：`viewerTopBar`/`viewerBottomBar` 内部用 `Spacer()` 把按钮推向
两端，但它们被 `HostedOverlay` 包成 `NSHostingView` 后，`NSHostingView`
默认按内容在"无约束"环境下的 **理想尺寸** 报告 `intrinsicContentSize`，
并不会自动撑满父 `VStack` 的横向空间——`Spacer()` 没有可撑的宽度，于是
整条 `HStack` 收缩到刚好包住两组按钮的宽度，挤在窄条左侧中间。

**修复**（`PhotoViewerView.swift` → `viewerOverlayBars`）：在每个
`HostedOverlay { viewerTopBar }` / `HostedOverlay { viewerBottomBar }`
**外面**追加 `.frame(maxWidth: .infinity)`（只设宽度，不设高度）。这样
`NSHostingView` 的宽度被撑满到与查看器同宽，`HStack` 内的 `Spacer()`
才有空间把按钮推到左上角/右上角，底部栏的文件名和操作按钮也才能分别
贴左、贴右。高度仍由内容自然高度决定，不会扩大覆盖层去盖住图片手势区。

#### 重构：拆分为两个文件，提高可维护性

之前三次问题的共同模式：有人调整查看器 SwiftUI 布局时，**顺手**改到了
`HostedOverlay`/`ViewerKeyCommandsView` 等 AppKit interop 代码（或者反过来），
而没意识到两边各有一套脆弱的协议（hitTest 链 / 第一响应者）。本次把它们
拆成两个文件：

- `PhotoViewerView.swift`：纯 SwiftUI 布局/状态/业务逻辑。
- `PhotoViewerInteropViews.swift`：纯 AppKit interop
  （`HostedOverlay`/`ZoomableImageView`/`SwipeAwareScrollView`/
  `LivePhotoPlayerView`/`ViewerKeyCommandsView`）。

两个文件顶部都有架构说明注释，互相指向对方和本文档。**改 SwiftUI 布局前，
先扫一眼 `PhotoViewerInteropViews.swift` 顶部注释；改 AppKit interop 前，
先扫一眼 `PhotoViewerView.swift` 顶部注释 + 本文档。**

## 给未来修改者的检查清单（Checklist）

修改 `PhotoViewerView.swift`（尤其是 `body`、`viewerOverlayBars`、`viewerTopBar`/
`viewerBottomBar`）或 `PhotoViewerInteropViews.swift`（`HostedOverlay`/
`ZoomableImageView`/`SwipeAwareScrollView`/`ViewerKeyCommandsView`）之前/
之后，请确认：

1. **覆盖层不能撑满全屏，但允许左右贴边**
   - 任何 `HostedOverlay { ... }` **内部**的内容，必须是"自然尺寸"的窄条/
     单个控件，**不能**带 `Spacer()` 让自身撑满，**不能**在内部
     `.frame(maxWidth/maxHeight: .infinity)` 扩展到覆盖图片区域。
   - 如果需要让某条工具栏在水平方向贴满（这样内部的 `Spacer()` 才能把
     按钮推到两端），把 `.frame(maxWidth: .infinity)` 加在
     `HostedOverlay { ... }` **外面**（只设宽度，不设高度），参见
     `viewerOverlayBars`。**高度永远不能撑满**，否则会盖住中间的图片
     手势区。
   - 新增覆盖层（比如新的浮动按钮/提示条）时，先想清楚它的 `NSHostingView.frame`
     会落在屏幕哪个区域，确认不会盖住中间的图片手势区。

2. **快捷键改在 `ViewerKeyCommandsView` 里，不要用 `.keyboardShortcut`**
   - 新增/修改查看器快捷键：去 `PhotoViewerInteropViews.swift` 里
     `ViewerKeyCommandsView.KeyCommandView.keyDown` 加 `case`，并通过
     构造参数传入对应回调。
   - 不要在 `viewerTopBar`/`viewerBottomBar` 的按钮上加 `.keyboardShortcut`——
     即使"看起来"能用，也可能在下次覆盖层结构调整后失效（详见"第 1/2 次"）。

3. **不要让 `ZoomableImageView`/`SwipeAwareScrollView` 抢第一响应者**
   - 如果给媒体内容相关的 `NSView` 子类新增功能，确认它的
     `acceptsFirstResponder` 仍然是 `false`（除非该功能本身需要键盘输入，
     且会在适当时机让出第一响应者给 `ViewerKeyCommandsView`）。

4. **不要破坏「首次打开即可用」的第一响应者时机**
   - 如果给 `KeyCommandView` 或其它需要第一响应者的视图新增/修改
     `viewDidMoveToWindow`/通知监听逻辑，确认仍然同时处理：
     (a) 视图刚加入窗口时（`viewDidMoveToWindow`），
     (b) 窗口真正变为 key window 时（`NSWindow.didBecomeKeyNotification`），
     (c) 后续被其他视图抢走时（`updateNSView` 自愈）。
     三者缺一，都会重现"首次打开延迟生效"。

5. **手动验证清单（无法在沙盒里编译，必须本地构建后手测）**
   - [ ] 查看器**首次打开**（冷启动后第一次进入，不要先打开过一次）：
     立即捏合缩放/拖拽/双击/滑动是否生效；立即按 ← → / Esc / Space /
     T/F/D/I 是否生效——不应该有"过一会才生效"的延迟
   - [ ] 返回按钮在左上角，上一张/下一张按钮在右上角
   - [ ] 文件名 + 播放/照片篓/收藏/删除/信息按钮在底部，分别贴左/贴右，
     且整条底部栏在窗口最下方
   - [ ] 静态图：捏合缩放、放大后拖拽平移、双击放大/还原
   - [ ] 静态图：未放大时双指横滑切换上一张/下一张
   - [ ] 键盘：← → 切换上一张/下一张
   - [ ] 键盘：Esc 返回照片墙
   - [ ] 键盘：Space 播放/暂停（视频/Live Photo）；静态图按 Space 无副作用
     （不报错、不响系统提示音）
   - [ ] 键盘：T（照片篓）、F（收藏）、D（删除）、I（信息面板）
   - [ ] 打开信息面板后，上述键盘快捷键仍然有效（验证第一响应者"自愈"逻辑）
   - [ ] 视频播放时，点击视频区域后键盘快捷键仍然有效
